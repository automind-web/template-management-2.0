# AI Management — инструкция публикации в ChatGPT Sites

## Что это

Рабочий кабинет задач компании с филиалами: сотрудник, руководитель филиала, директор.
Полный стек в одном репозитории: React + Tailwind CSS 4 + shadcn/ui (фронтенд),
серверные операции в стиле Next.js App Router на **vinext** (Vite), база **D1** (SQLite) через
Drizzle ORM, файлы в **R2**. Собирается в Cloudflare Worker `dist/server/index.js` (ES-модуль, экспорт `fetch`).

Вход — **собственные логин и пароль** (не «Вход через ChatGPT»). Аккаунт ChatGPT или Google посетителю не нужен.

## Требования

- Node.js **22.13 или новее**
- Сборка: `npm ci && npm run build`
- Результат: `dist/server/index.js` (Worker), `dist/client/` (статика), `dist/.openai/hosting.json` и `dist/.openai/drizzle/` (миграции)

## Привязки (`.openai/hosting.json`)

```json
{ "d1": "DB", "r2": "BUCKET" }
```

| Привязка | Тип | Назначение |
|---|---|---|
| `DB` | D1 (SQLite) | Все данные: компания, филиалы, пользователи, сессии, задачи, история, очередь уведомлений |
| `BUCKET` | R2 | Содержимое файлов (вложения, фото, голос). Метаданные — в D1 |

Формат файла взят из стартового шаблона Sites (vinext-starter): поля `d1` и `r2` содержат имена привязок.
`project_id` в репозитории **нет** — Sites дописывает его сам после создания проекта.
> Сверить: если в вашей версии Sites формат `hosting.json` отличается, приведите его к шаблону, имена привязок оставьте `DB` и `BUCKET`.

## Миграции

- Файлы: `drizzle/0000_init.sql`, `drizzle/0001_task_search.sql`, `drizzle/0002_due_time_can_invite.sql`, … (порядок — `drizzle/meta/_journal.json`).
- Сборка копирует их в `dist/.openai/drizzle/`; Sites применяет их к D1 **по порядку, до** того как новая версия получит трафик.
- Новая компания стартует с **чистой БД**: миграции создают только схему, без примеров и тестовых аккаунтов.
- Схема меняется **только новыми миграциями** (`npm run db:generate -- --name <описание>`). Применённые файлы не редактировать: откат версии возвращает код, но не данные.

## Секрет сайта (Settings → Secrets)

Нужен **один** секрет — `OWNER_ACTIVATION_CODE` (длинная случайная строка). Значение в репозиторий не кладётся
(см. `.env.example`). Он нужен для первого запуска (`/setup`) и для шифрования ключей, которые директор вводит на сайте.

> Если код активации поменять, сохранённые ключи WhatsApp и OpenAI перестанут расшифровываться —
> директору нужно будет ввести их заново в «Настройки → Помощник».

Всё остальное настраивается **на самом сайте**, только директором:

| Где | Что |
|---|---|
| «Настройки → Компания» | Название, логотип (файл), фирменный цвет, город (часовой пояс), рабочие дни, проверка выполненных задач, видимость задач коллег |
| «Настройки → Филиалы» | Создать, переименовать, убрать в архив |
| «Настройки → Сотрудники» | Пригласить (ссылка + «Отправить в WhatsApp»), роль, филиал, должность, **номер WhatsApp**, ссылка для нового пароля, закрыть/вернуть доступ |
| «Настройки → Помощник» | Ключ WhatsApp (Whapi), ключ OpenAI, уровень помощника (модель), имя и пожелания к помощнику |

Ключи хранятся в D1 в зашифрованном виде (AES-GCM) и в браузер не передаются — видно только «••••» и последние 4 символа.
Ключи push-уведомлений создаются автоматически. `WHAPI_API_URL` (не секрет) нужен только тестовому окружению с заглушкой.

## WhatsApp-помощник

1. Директор: «Настройки → Помощник» → вставляет ключ WhatsApp из кабинета Whapi и нажимает «Сохранить изменения».
   Сайт проверяет ключ, сам прописывает в Whapi адрес для входящих сообщений и подставляет рабочий номер.
2. Там же — ключ OpenAI и уровень помощника. Один ключ WhatsApp и один ключ OpenAI работают для всех сотрудников.
3. Директор указывает номер WhatsApp сотрудника в «Настройки → Сотрудники» (или сотрудник привязывает его сам кодом в «Профиле»).

Бот отвечает **только** сотрудникам с действующим доступом, чей номер есть в системе, и только в пределах их собственных
задач и прав. Незнакомые номера и сотрудники с закрытым доступом ответа не получают.
Раздел «Помощник» на сайте использует те же пожелания и тот же уровень (модель) напрямую, без WhatsApp.

## Напоминания и расписание

Фоновых процессов нет: очередь уведомлений хранится в D1 и обрабатывается короткими порциями после
запросов к сайту (не чаще раза в 15 секунд) и при открытии «Уведомлений». Worker экспортирует `scheduled()`:
если в Sites доступен запуск по расписанию, включите его (например, каждые 5 минут) — тогда напоминания
уходят и без посещений сайта.

## Доступ к сайту

В настройках доступа Sites сайт должен быть **открыт для всех (Public)**. Иначе Sites покажет свой вход
и форма входа кабинета не откроется. Права проверяет сам кабинет на каждом запросе.

## Первый запуск: как создать первого директора

1. Задайте секрет `OWNER_ACTIVATION_CODE` и опубликуйте сайт.
2. Откройте `https://<адрес-сайта>/setup` (или ссылку «Первый запуск» на странице входа).
3. Введите код активации, название компании и срок действия ссылки (по умолчанию 72 часа).
4. Получите **одноразовую** ссылку-приглашение директора. Повторный выпуск отзывает прежнюю.
5. Откройте ссылку, задайте имя, логин и пароль. Приглашение гасится только успешной регистрацией.
6. Директор создаёт филиал («Настройки → Филиалы») и приглашает людей в «Настройки → Сотрудники».
   Логотип, цвет, город и рабочие дни — «Настройки → Компания»; WhatsApp и ИИ — «Настройки → Помощник».

После активации директора страница `/setup` закрывается (повторно директора этим путём не создать).

## Проверка после публикации

- `GET /api/health` → `{"ok":true,"build":"1.0.0","schema":"0002_due_time_can_invite","bindings":{"db":true,"bucket":true}}`
- Чистый браузер открывает адрес сайта → форма входа кабинета.
- `/manifest.webmanifest` и `/sw.js` отдаются — сайт можно установить как приложение.

## Локальная разработка

```bash
npm ci
cp .env.example .dev.vars            # заполнить OWNER_ACTIVATION_CODE
npm run db:migrate:local             # миграции в локальную D1 (Miniflare)
npm run dev                          # http://localhost:5173
```

| Команда | Что делает |
|---|---|
| `npm run build` | Сборка + проверка артефакта (`scripts/check-artifact.mjs`) |
| `npm run db:check` | Применяет все миграции к пустой SQLite в памяти, проверяет чистый старт |
| `npm test` | Юнит-тесты (пароли, сроки по часовому поясу, даты помощника, web push) |
| `npm run smoke:all` | Все сквозные сценарии на чистой локальной БД, WhatsApp — на заглушке Whapi (**только для разработки**) |
| `npm run db:reset:local` | Пересоздаёт локальную D1 разработки |

### Быстрые действия, карточка сбоку и уведомления

- Переносы в канбане и редактирование показывают результат сразу. Пока сервер сохраняет задачу, карточка серая; ошибки отмечаются красным уведомлением, неудачное изменение откатывается. Запоздалое обновление списка не перезаписывает более новую задачу.
- Из списка, статистики, помощника и входящих задача открывается в боковой панели. Основной экран остаётся на месте, включая поиск, фильтры, черновики и прокрутку. Старые адреса `/tasks/:id` открывают ту же панель через `/tasks?task=:id`.
- Необязательный результат не вызывает форму при переносе. Обязательные текст, вложение и причина возврата проверяются также на сервере.
- В разделе «Уведомления» есть установка приложения и тестовая отправка через настоящий Web Push. На iPhone/iPad нужно добавить сайт на экран «Домой» из Safari, открыть установленное приложение и разрешить уведомления (iOS/iPadOS 16.4+).
- VAPID создаётся атомарно, подписка восстанавливает привязку после входа; отозванные и истёкшие сессии не получают текст задач. Временные ошибки доставки повторяются, недействующие адреса удаляются из доставки.
- Для доставки напоминаний при закрытом сайте требуется планировщик Cloudflare: в `vite.config.ts` задан `triggers.crons = ["* * * * *"]`, обработчик `scheduled` включён в Worker. При размещении через ChatGPT Sites необходимо, чтобы хостинг применял Cron Triggers из конфигурации Worker. Наличие функции `scheduled` само по себе не запускает расписание.
- Статус фонового расписания в интерфейсе основан на успешном выполнении `scheduled` за последние три минуты. Если статус не подтверждён, доставка запланированных напоминаний без посещения сайта не считается проверенной. Запросы посетителей также обрабатывают очередь, но не подменяют этот статус.

Проверки: `npm run typecheck`, `npm test`, `npm run db:check`, `npm run build`. Регрессии кэша и обязательности формы находятся в `test/task-cache.test.ts`.
